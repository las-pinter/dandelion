# Dandelion WebSocket API

Verified against the implementation and its tests on 2026-11-23.

## Endpoint

`GET /api/ws` upgrades to one multiplexed WebSocket. The handshake must carry:

- a live session cookie (`__Host-dandelion_session` on HTTPS,
  `dandelion_session` on the loopback development origin);
- an `Origin` header matching the resolved public origin, or
  `Sec-Fetch-Site: same-origin`.

Missing session → `401`. Missing or foreign origin → `403`. The route sits in
the protected router, so the same middleware as the rest of the API applies.

The handshake authenticates once, but the socket does not outlive the session:
a logout or logout-all closes matching live sockets immediately, and every
socket revalidates its session row every 30 seconds. A session deleted or
expired by any other means (including `dandelion auth reset`) is therefore
closed within 30 seconds.

All messages are JSON text frames. The server rejects frames larger than
64 KiB. TypeScript mirrors of the Rust types live in `web/src/api/gen/ws/`
(generated by `dandelion ts-types`, not hand-edited).

## Client → server

```json
{"type": "subscribe", "topics": ["system.metrics", "agents"]}
{"type": "unsubscribe", "topics": ["agents"]}
{"type": "ping"}
```

- `subscribe` adds to the connection's set; `unsubscribe` removes.
- Topic names are 1–64 characters: ASCII letters, digits, `.`, `_`, `-`.
- A connection may hold at most 32 topics.
- Invalid input returns an `error` message; it does not close the socket.

## Server → client

```json
{"type": "welcome", "topics": []}
{"type": "subscribed", "topics": ["agents", "system.metrics"]}
{"type": "unsubscribed", "topics": ["system.metrics"]}
{"type": "event", "topic": "system.metrics", "data": {"cpu": 42}}
{"type": "error", "message": "the topics list is empty"}
{"type": "pong"}
```

`subscribed` and `unsubscribed` carry the full current set, sorted. `event`
carries only topics this connection has subscribed to; `data` is opaque to the
transport.

## Topics

| Topic | Payload | Cadence |
|---|---|---|
| `system.metrics` | `LiveSample`: `{ snapshot, point }` — the full `Snapshot` plus the compact `MetricsPoint` the server also stores | One per second while the collector runs |
| `agents` | `{ kind: "resync", terminals: [...] }` when the server's backend subscription starts or restarts, `{ kind: "terminal", terminal, change }` per backend event, `{ kind: "claude" }` when a Claude Code session's state or usage changes, and `{ kind: "backend" }` when the startup retry adopts a backend that was not up yet | On every backend or session change |

A browser that subscribes later does not receive that resync; it takes its
first paint from `GET /api/agents` and follows the topic for changes.

Stored history is read over REST: `GET /api/system/history?range=1h` returns
second points, `?range=7d` returns minute aggregates, and
`GET /api/system/latest` returns the newest snapshot (`503` until the first
sample). SQLite keeps one hour of seconds and one week of minutes; a restart
loses only the minute that was open in memory.

## Backpressure and limits

- Each topic has its own bounded broadcast channel (256 events). Publishers
  never block. A flood on one topic therefore cannot lag or disconnect a
  client subscribed only to other topics.
- Event payloads are limited to 64 KiB of serialized JSON; a larger payload is
  dropped at publish time and logged.
- Each connection writes events directly and allows a single write to block
  for at most 5 seconds. After that the connection closes.
- A receiver that lags on a topic it subscribed to closes its connection.
- Slow or stalled clients therefore cannot block publishers or other clients.

## Terminal socket

Each open shell has its own socket, `GET /api/terminals/{id}/ws`, deliberately
separate from the hub: a terminal carries raw bytes, not topic-tagged JSON.
The handshake uses the same session cookie and origin check as `/api/ws`, and
the socket revalidates its session every 30 seconds and closes on logout. One
socket may attach to a terminal at a time; a second handshake gets `409
terminal_busy`. Binary frames carry terminal bytes both ways; text frames carry
`{"type":"resize","cols":N,"rows":N}`. Frames are capped at 64 KiB. The shell
ends when the socket does, and its whole process session is killed so a
background child cannot keep the pseudo-terminal open.

## Agent socket

Each agent pane has its own socket, `GET /api/agents/{terminal}/ws`, with the
same session-cookie and origin handshake, 30-second session recheck, logout
close, and 64 KiB frame cap as the other sockets. The server attaches as an
observer: the pane never types into or resizes the agent's real terminal, so
control stays in the audited action API (`POST /api/agents/action`). Binary
frames carry pane bytes both ways; text frames carry
`{"type":"resize","cols":N,"rows":N}`, which an observer accepts without
resizing anything. The server sends `{"type":"resized",...}` when the backend
reports a size, and `{"type":"closed","reason":…}` or
`{"type":"error","message":…}` before the stream ends.

`GET /api/agents/{terminal}/screen` returns the visible screen only. History is
never read: herdr-core scrolls a full-screen program to stitch it, and
scrolling is input to that program.

## Tests

`crates/server/tests/ws.rs` proves the handshake auth and origin checks
(including the `Sec-Fetch-Site` fallback), topic filtering and isolation, the
cumulative 32-topic cap, ping/error handling, oversized frames, logout and
logout-all closing live sockets, and that a slow client is disconnected while
a fast one keeps receiving.

`crates/server/tests/terminals.rs` proves the terminal handshake (including a
foreign-origin refusal), binary input/output, resize propagation, the busy
refusal, and that a socket close or `DELETE` ends the shell.

`crates/server/tests/agents/` proves the agent routes and their audit rows
with a fake backend, and the agent handshake (session and origin refusals),
the observer attach, output, input, resize, and the close that ends it.
